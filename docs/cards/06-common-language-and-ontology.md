# 共同语言、知识图谱与Ontology

## 管理结论

跨部门AI问题经常不是“模型不懂”，而是企业没有统一对象、口径、关系和责任。

## 三个层次

- **业务定义**：什么叫供应商、准时到货、有效合同和重大异常。
- **对象与关系**：供应商法人、工厂、订单、物料、合同和责任岗位如何连接。
- **规则与动作**：满足什么条件可以查询、建议、提交审批或变更订单。

知识图谱表达具体对象、概念及关系；Ontology（本体）定义对象类型、关系与语义约束。企业软件可以在其上连接业务规则和动作，但本体本身不会赋予操作权限。并非所有场景都需要完整Ontology：范围小、规则稳定的任务可以先用数据字典、对象表和决策表验证价值。

## 用一笔订单分清三件事（P45）

Ontology定义“订单需要物料、供应商供应物料”等类型与关系；知识图谱记录“订单O-0915-K需要物料K共450件”等具体事实；SHACL检查这些记录是否满足声明条件，例如数量必须是数值、订单必须关联物料。检查通过只说明记录满足这些条件，不证明450件真实无误，也不允许系统自动下单。

## 管理决定

- 谁拥有定义权，谁负责处理冲突？
- 定义变化后，哪些检索、规则、评测和Agent需要同步更新？
- 是否存在一个可供业务、数据和技术共同审阅的最小表示？

## 同一笔订单上的技术分工

订单O-0915-K需要物料K共450件，已到300件，余量150件预计17日到达，有效条款要求15日齐套可用。

- 类型定义订单、物料、供应商和合同条款。事实记录具体对象、数量、时间与关系。
- 查询连接有效条款和当前物流，取得同一订单的证据。语义推理可以补出声明规则所蕴含的关系。
- 约束验证检查数量类型、必需关系和其他显式条件；缺少质量放行证据时，不能据此推定已可用。
- 业务规则和动作执行另行检查当前授权。关系图与验证报告都不会自动修改订单。

跨源连接前还需实体对齐。AI可比较名称、地址等字段并提出匹配候选，法人标识冲突则核对登记。研究依据：[Ditto，2020](https://arxiv.org/html/2004.00584v3)；约束验证依据：[W3C SHACL](https://www.w3.org/TR/shacl/)。订单与匹配名称为课程合成。

## 方法年份与生产能力

Ditto（2020）是实体匹配方法来源，不是整幅企业架构的出处。[AWS Entity Resolution](https://docs.aws.amazon.com/entityresolution/latest/userguide/create-matching-workflow.html)已提供规则、机器学习及服务商匹配工作流。企业上线仍要实测误合并、漏匹配，并建立冲突复核责任。

SHACL是“检查图数据是否满足声明条件的约束语言”，2017年为W3C标准发布年份。它可以检查字段、类型和关系条件，不能证明原始事实真实，也不授予业务操作权限。

| 比较维度 | 数据字典、对象表与决策表 | 知识图谱与Ontology |
|---|---|---|
| 关系复杂度 | 固定关系、局部任务便于起步 | 适合多类对象与复杂跨源关系 |
| 语义复用 | 按表与应用维护口径 | 显式类型与关系可跨任务复用 |
| 维护能力 | 业务和数据团队易于共同审查 | 需持续维护语义、约束与映射 |
| 成本 | 初期通常较轻，跨域后需维护多处映射 | 初期建模与治理投入较高，复用收益需实测 |

两种表示可以组合。先按任务确定关系复杂度与团队维护能力，再决定范围；标准年份不能替代成熟度判断。以上选型比较是课程归纳，官方能力核验2026-09-18。
